# prod 資料交付規格（給排程專案）

儀表板（本 repo 的 `prod/`）對排程專案的需求：要拿到什麼資料、放在哪裡、怎麼放上來。
排程怎麼向平台撈資料，寫在排程專案自己的文件，不在這裡。

- 儀表板網址：`https://arthurhsuadvmeds.github.io/rapid-response-platform-dashboard/prod/`
- 資料檔：`prod/data.json`（與 `prod/index.html` 同層；儀表板只讀這一個檔）
- 格式版本：`schemaVersion: 1`（2026-11-09 訂）
- 標 ★ 的是還沒確認的地方，問題集中在第 5 節。

---

## 0. 開始排程前要先決定：repo 與網站都是公開的

- 2026-11-09 確認 repo `ArthurHsuAdvmeds/rapid-response-platform-dashboard` 是 **public**。
  GitHub Pages 網站本身沒有登入機制（repo 改成 private，Pages 網址照樣任何人都能開），知道網址就能下載 `prod/data.json`。
- 每一次 push 都永久留在 git 歷史裡；事後刪檔、改 private，都收不回已經被下載或 fork 的內容。
- 資料是精神醫療緊急個案：座標（目前精確到公尺級）＋年齡＋性別＋通報時間，合起來足以指認到人，屬個資法第 6 條的醫療特種個資。
- 開始定期 push 前先選一種做法，選定後把結果寫回這一節：
  1. **明文照推**（目前的設計）：需要醫院／法遵同意，並至少做到第 4 節的資料最小化。
  2. **加密後再推**：排程端用密碼加密 data.json，儀表板開頁時輸入密碼、在瀏覽器內解密。
     仍然是 GitHub Pages＋repo 裡的 JSON，但公開的只有密文；本 repo 要加解密畫面，排程端多一步加密。
  3. **換有權限控管的託管**：private repo 搭配需要登入的靜態網站服務，或放院內主機。

## 1. 需要排程做的事

1. **每次都是全量快照**：撈平台上**全部**緊急醫療通報（不限日期），整份覆寫 `prod/data.json`。不做增量、不跟舊檔合併。
   案件狀態會變（待派 → 已派 → 結案），作廢的通報也要消失，整份重產最不會錯。
2. **每次執行都更新 `updatedAt` 並 push**，就算案件內容一筆都沒變。
   儀表板拿 `updatedAt` 的日期當「今天」（本日／本月／本季／本年度的基準），也拿它判斷資料新不新：
   距今超過 **48 小時**，頁首會顯示「資料已 N 天未更新」。所以排程**至少每天跑一次**；
   跑更頻繁也可以，每次 push 會觸發一次 Pages 部署（約 1 分鐘）。
3. **push 前先檢查，不過就不要推**（保留上一版、發告警）：
   - 是標準 JSON（不帶註解、沒有結尾逗號）；`schemaVersion` 是 `1`；`emg` 是陣列。
   - 每筆都有 `reportId`（不重複）與可解析的 `timePoint.reportedAt`。
   - 筆數不是 0，也沒有比上一版明顯變少（門檻由排程專案決定）。全量快照照理只增不減，突然變少多半是撈資料出錯，推上來儀表板就跟著變空。
4. **只動 `prod/data.json`**，不改 repo 裡的其他檔（程式、文件、workflow）。
5. **git**：
   - push 前 `git pull --rebase`（儀表板開發也會推 `main`）；被拒絕就重新 pull 再推，**不要 force push**。
   - commit message 固定格式，方便在 log 裡篩：`prod data 2026-11-09 06:00（緊急醫療 123 筆）`。
   - 用只對這個 repo 有寫入權的 deploy key（或 fine-grained token，只開 Contents: Read and write）。`main` 若設了分支保護，要讓它能直接 push。
   - 平台網址、帳密、token、內網 IP、執行 log 一律不可進 repo。
6. **推完怎麼確認**：Actions 的「Deploy GitHub Pages」綠燈後（約 1 分鐘）打開儀表板，
   頁首「資料更新」是這次的時間、「總案件數」符合預期，而且沒有黃色提示（代碼無法對應、reportId 重複…）。

## 2. 檔案怎麼放

- 只有一個檔：`prod/data.json`，UTF-8（不要 BOM）、LF 換行。
- 建議**一筆通報一行**，依 `timePoint.reportedAt`、再依 `reportId` 排序，每筆的欄位順序固定（照 3.2 表格的順序）。
  git diff 只會出現有變動的那幾筆，檔案也只有縮排排版的一半大（目前每筆約 0.4 KB）：

  ```text
  {"schemaVersion":1,"updatedAt":"2026-11-09T06:00:05+08:00","dataStart":"2026-10-01",
  "emg":[
  {"reportId":"20261105093012","reporterDepartment":3,"caseInfo":{…},"assess":{…},"acceptWay":1,"timePoint":{…},"status":1,"StatisfactionAvg":4.5},
  {"reportId":"20261105141508", …}
  ]}
  ```

### 為什麼只用一個檔、什麼時候才拆

- 儀表板是唯讀的，資料每次整份重產。正規化是為了「改一處不必同步改多處」，這裡沒有更新、只有重產，
  拆成人／量表／時間點／代碼表好幾個檔只會多出 join，沒有好處。
- 每一頁都要同時用到全部案件（日期篩選、各狀態件數、地圖），拆了也是一次全部載入。
- 大小不是問題：每年 1,000 筆約 0.4 MB，十年也才幾 MB，GitHub Pages 傳輸時還會壓縮。
- **要不要拆檔，只看「誰產生、多久產生一次」**：
  - 同一支排程、同一個來源、同一次執行產生的 → 同一個檔，用最外層的鍵分類（現在的 `emg`，之後的優化計畫再加一個鍵）。
  - 不同來源或不同頻率（例如之後的 HIS 資料由另一支程式產生）→ 在 `prod/` 另開一個同層的檔（例如 `prod/his.json`），外框一樣有 `schemaVersion`、`updatedAt`，
    兩邊各自顯示更新時間，一邊壞了不影響另一邊。
  - 真的大到拖慢載入（例如超過 10 MB）再考慮依年度拆案件陣列，現在不用。

## 3. 格式（schemaVersion 1）

### 3.1 最外層

| 欄位 | 必填 | 型別 | 說明 |
| --- | --- | --- | --- |
| `schemaVersion` | ✓ | 整數 | 固定 `1`。儀表板看到不認得的版本會整頁顯示錯誤、不畫任何數字 |
| `updatedAt` | ✓ | 字串 | 排程向平台撈資料的時間，ISO 8601，**帶 `+08:00`**，例如 `2026-11-09T06:00:05+08:00`。頁首顯示「資料更新」，日期是本日／本月…的基準 |
| `dataStart` |  | 字串 | 平台開始收案日 `YYYY-MM-DD`。指揮板預設區間的起點、年度結案率從這一年列起；省略時取最早一筆通報的日期 |
| `emg` | ✓ | 陣列 | 緊急醫療通報，一筆一個物件，見 3.2 |

`asOf`（覆寫「今天」）與 `sample: true`（頁首標示「範例資料（虛構）」）只給測試用，排程不要填。其他鍵儀表板目前不讀。

### 3.2 `emg` 每一筆

- 時間一律 `YYYY-MM-DDTHH:mm:ss`。不帶時區的當作臺北時間，帶時區也可以。
- 沒有值給 `null`，不要給空字串，也不要省略整個子物件。

| 欄位 | 型別 | 說明 | 儀表板用在 |
| --- | --- | --- | --- |
| `reportId` | 字串 | 通報識別碼，**唯一、不會變** | 地圖點位提示、重複檢查 |
| `reporterDepartment` | 整數 | 通報者所屬網絡，見 3.3 ★ | 通報者頁 |
| `caseInfo.county` | 字串／null | **新增，選填但建議給**：縣市全名，例如 `臺北市`、`新北市`（台／臺都可以） | 行政區長條圖、地圖全臺層級 |
| `caseInfo.dict` | 字串／null | 行政區：`大安`、`大安區`、`新北市板橋區` 都可以；臺北市以外請給完整名稱（`板橋區`、`竹北市`） | 行政區長條圖、地圖 |
| `caseInfo.longitude`／`latitude` | 數字／null | WGS84 座標，兩個都有才畫點；座標相同（小數 5 位）的通報合併成一個點。精度見第 4 節 | 地圖點位 |
| `caseInfo.gender` | 整數／null | 見 3.3 | 性別 |
| `caseInfo.age` | 整數／null | 通報當時的年齡（不要給生日） | 年齡 |
| `assess.CTRS` | 整數／null | 風險檢傷評估的等級，見 3.3。**同時當作「初評風險」** ★ | 風險頁、效率頁總覽、地圖點位顏色 |
| `assess.GAF`／`BSRS5`／`CGIS` | 整數／null | 各量表的等級（不是原始分數），見 3.3 | 風險頁 |
| `acceptWay` | 整數／null | 受理方式，見 3.3；還沒完成受理方式為 `null` | 效率頁 |
| `timePoint.reportedAt` | 時間 | 網絡完成通報。**必填，所有日期篩選與時效指標的起點**；無法解析的筆數會被排除並在頁首提示 | 全部 |
| `timePoint.assignedAt` | 時間／null | 完成指派醫師／護理師；未指派為 `null` | 待派／已派、派案時間 |
| `timePoint.acceptedAt` | 時間／null | 首次完成「受理方式」表單（＝處理完成）；未完成為 `null` | 效率頁 |
| `timePoint.outsideAt` | 時間／null | 出勤單上填的實際出勤時間；沒有出勤為 `null` | 出勤流程 |
| `status` | 整數 | 見 3.3 | 各狀態件數、結案率 |
| `StatisfactionAvg` | 數字／null | 滿意度平均分 1–5；未填寫為 `null`。欄位名沿用平台拼法，寫成 `SatisfactionAvg` 也可以 | 通報者頁 |

一筆完整的例子（虛構，實際檔案裡寫成一行）：

```json
{"reportId":"20261105093012","reporterDepartment":3,
 "caseInfo":{"county":"臺北市","dict":"北投","longitude":121.501,"latitude":25.132,"gender":20,"age":52},
 "assess":{"CTRS":1,"GAF":2,"BSRS5":0,"CGIS":1},
 "acceptWay":1,
 "timePoint":{"reportedAt":"2026-11-05T09:30:12","assignedAt":"2026-11-05T09:41:03","acceptedAt":"2026-11-05T11:02:47","outsideAt":"2026-11-06T14:00:00"},
 "status":1,"StatisfactionAvg":4.5}
```

### 3.3 代碼

| 欄位 | 代碼 |
| --- | --- |
| `reporterDepartment` | ★ 暫定：`0` 社政、`1` 警察、`2` 民政、`3` 衛政、`4` 教育、`5` 消防、`6` 勞政、`8` 其他；`7` 尚未對應。表上沒有的代碼列為「代碼 N（未對應）」並在頁首提示 |
| `assess.*` | `0` 低風險／輕度、`1` 中風險／中度、`2` 高風險／重度、`3` 其他（不列入統計） |
| `caseInfo.gender` | `10` 男、`20` 女，其他算「不明」 |
| `acceptWay` | `0` 電話、`1` 電話＋出勤 |
| `status` | `0` 未結案（再依 `assignedAt` 有沒有值分成待派／已派）、`1` 已結案、`2` 未開案／結案（緊急醫療目前不會出現） |

量表等級的切點（使用者提供；平台只給原始分數時，排程依此換算）：

| 量表 | 輕度 `0` | 中度 `1` | 重度 `2` | 其他 `3` |
| --- | --- | --- | --- | --- |
| CGI-S | 1–3 | 4 | 5–7 | — |
| BSRS-5 | 0–9 | 10–14 | 15–24 | — |
| GAF | 61–100 | 41–60 | 1–40 | 其他數字（不列入統計） |

風險檢傷評估（CTRS）的分級規則沒有提供，照平台給的等級。

## 4. 不可放進來的資料（第 0 節選哪種做法都適用）

- 不可放：姓名、身分證字號、出生日期（只給年齡）、電話、地址文字、病歷號、平台帳號、通報人與醫護人員的姓名，
  以及任何自由文字欄位（備註、事件描述、處置紀錄——常夾帶個資）。
- 儀表板用不到的欄位就不要放；要加欄位，先在這份文件定義（見第 6 節）。
- ★ 座標建議四捨五入到小數 **3 位**（約 100 公尺）：地圖仍看得出熱點，只是同一格內的通報會合併成一個點。是否採用待決定。
- 測試帳號建立的、已作廢的通報不要放。

## 6. 之後要加資料時

- **優化計畫**：同一來源、同一支排程 → 同一個檔加一個陣列（例如 `opt`）。
  共用的欄位沿用 `emg` 的名稱與代碼（`reportId`、`reporterDepartment`、`caseInfo`、`assess`、`timePoint.reportedAt`／`assignedAt`、`status`）；
  優化計畫特有的時間點與結果（衛生局回覆單、不轉介覆核、醫療機構回覆單、訪視、追蹤量表…）等儀表板要恢復那些頁面時再訂。
- **HIS 衍生資料**（結案後就醫、SNQ）：由另一支程式、另一個頻率產生時 → `prod/his.json`，外框同樣有 `schemaVersion`、`updatedAt`。
  以 `reportId` 對應案件；**身分證比對在排程端做完，不放進檔案**；SNQ 只放彙總數字。
- **平台使用率**：只放各單位的總帳號數、曾登入帳號數，不放帳號明細。
- **版本規則**：
  - 新增選填欄位 → 版本不變，儀表板會略過不認得的欄位。
  - 改名、刪欄位、改代碼意義 → `schemaVersion` 加 1。先讓儀表板同時支援新舊版本並上線，排程再切換。
  - 每次改格式都先改這份文件，兩邊照文件實作。
